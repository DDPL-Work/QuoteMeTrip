One key point from the approved workflow is that route selection comes before the form, and the calculated route, distance, stop order and recommended duration should flow into the subsequent request rather than being re-entered manually.

The API already has separate route and travel-request operations, so keeping those responsibilities distinct in the frontend will also make Phase 4 much easier to maintain: route APIs manage route state, while travel-request APIs manage the draft/request lifecycle.

This phase should be treated as the largest Traveller-side foundation phase so far. Once it is signed off, Phase 5 can begin with Agency Matching against a stable, real submitted travel request.
